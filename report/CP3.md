## 2. 設計內容

### 2.1 語意規格

`rd = min_signed(rs1, rs2)`。兩個輸入均為 32-bit 二補數有號整數，定義域與結果範圍皆為 `[-2147483648, 2147483647]`。相等時寫回共同值；零、正負混合及極值都依有號大小比較，不做特殊飽和。MIN 只比較與選值，不計算輸入差值，因此沒有算術溢位。

完整來源值讀取、`rd` 重疊與 `x0` 寫回規則，以及虛擬碼、七組測試向量、baseline 片段與指令數，見[工作二正式規格](../instructions/MIN/README.md)。該文件列出的七筆範例包含相等、零、負數與上下極值，超過至少三筆、含一筆邊界的要求。

編碼確認紀錄：目前小組採用 `funct7=0000000`、`funct3=000`、`opcode=0001011`（custom-0）。**小組採用，教師分配來源待核對。** HOMEWORK.md 第4節已固定opcode為0x0B，但未在目前可取得來源中找到MIN的教師正式funct分配或核准證據；組員草稿的分配自述不代替公告。此處只記錄本人提供的小組確認，完整編碼及來源核實仍由工作三／組長處理，不改其他組員規格或程式。

### 2.2 虛擬碼與範例

```text
a = signed32(rs1 的來源舊值)
b = signed32(rs2 的來源舊值)
result = rs1 的舊位元模式 if a < b else rs2 的舊位元模式
if rd 不是 x0:
    將 result 的 32 個位元寫回 rd
```

| rs1 | rs2 | 預期 rd | 覆蓋情況 |
|---:|---:|---:|---|
| 3 | -2 | -2 | 正負混合 |
| 5 | 5 | 5 | 相等 |
| 0 | -1 | -1 | 零及有號比較 |
| 2147483647 | -2147483648 | -2147483648 | 32-bit 上下極值 |

### 2.3 baseline 與設計理由

既有 baseline 以有號 `blt` 選路徑，不跳時用 `addi` 複製第二個輸入，最後以 `jalr` 返回。靜態核心／函式指令數為 2／3；原 14 筆測資的動態路徑推算為 24／38。推算範圍不含呼叫端及測試框架，函式數包含返回。[規格中的 baseline 段落](../instructions/MIN/README.md#4-rv32im-baseline-與語意一致性)附原碼與計數表；來源、暫存器規則與計數範圍見下一節。

### 2.4 MIN 技術說明與計數範圍

在工作二中，我主要確認 MIN 指令的有號整數比較規則。MIN 會比較 rs1 與 rs2 的 32-bit 數值，並將較小的值寫入 rd。例如 rs1 為 -5、rs2 為 9 時，結果應為 -5。如果使用無號比較，負數的位元表示可能被判斷成很大的正數，造成結果錯誤。

另外，MIN 是從兩個輸入值中選擇其中一個，不需要透過減法結果判斷大小，因此不會產生算術溢位。當 rd 為 x0 時，寫入不會改變 x0 的值；當 rd 與來源暫存器重疊時，則必須確保比較使用的是寫回前的來源值。

我也理解靜態指令數與動態指令數的差別：靜態是指定統計範圍內、偽指令展開後的機器指令條數；動態則是指定輸入執行時真正經過的指令次數，因此會受到分支結果影響。兩者都須說明是否包含返回、呼叫端與測試框架。

上述為本人本次確認採用的理解文字，不宣稱教師已驗證個人理解。極值、相等與暫存器完整定義仍以第2.1節及正式規格為準；C原始碼沒有固定機器指令數。本文Branch核心／含返回的靜態數2／3、原14例動態24／38，與CP2保存C編譯函式的4／46是不同來源，不因函式符號同名而混用，也不直接代表週期或時間加速。

### 2.5 自訂指令格式與機器碼

介面為 `min rd, rs1, rs2`，rs1、rs2 提供來源，rd 接收較小值。R-type 欄位由高至低為 funct7[31:25]（7位）、rs2[24:20]（5位）、rs1[19:15]（5位）、funct3[14:12]（3位）、rd[11:7]（5位）、opcode[6:0]（7位）。

固定 opcode 為 custom-0，0001011（0x0B）。以下採小組目前使用的 funct7=0000000、funct3=000；教師正式分配來源待核對，若值不同須同步重算。

| Assembly | 二進位（funct7 rs2 rs1 funct3 rd opcode） | Hex |
|---|---|---|
| min x10,x10,x11 | 0000000 01011 01010 000 01010 0001011 | 0x00B5050B |
| min x12,x13,x14 | 0000000 01110 01101 000 01100 0001011 | 0x00E6860B |
| min x15,x16,x17 | 0000000 10001 10000 000 01111 0001011 | 0x0118078B |

編碼公式為 `(funct7<<25)|(rs2<<20)|(rs1<<15)|(funct3<<12)|(rd<<7)|opcode`。反解時依各欄位右移並取指定寬度；第三筆還原為 (funct7,rs2,rs1,funct3,rd,opcode)=(0,17,16,0,15,11)。機器碼指定暫存器，不包含執行前的輸入數值。[編碼附件](../instructions/02_MIN/report/自訂指令格式與機器碼.md)提供完整欄位與反解表。

自訂函式的設計片段為 `min a0,a0,a1` 接 `jalr x0,0(ra)`；不表示目前 assembler 或處理器已支援這個助記符。

## 3. 結果與分析

### 3.1 統一範圍比較

各版本皆排除呼叫端、參數準備及測試框架。核心列全部排除返回；函式列全部包含每次一條 jalr 返回。動態為原始14筆各執行一次，靜態以偽指令展開後的機器指令計算。

| 版本 | 核心靜態 | 函式靜態含返回 | 核心動態14筆 | 函式動態14筆含返回 | 動態條件分支14筆 | 性質 |
|---|---:|---:|---:|---:|---:|---|
| C baseline（編譯後 min_s32） | 3 | 4 | 32 | 46 | 14 | 保存 ELF 直譯計數 |
| Branch（min_branch） | 2 | 3 | 24 | 38 | 14 | 保存 ELF 直譯計數 |
| Branchless（min_branchless） | 5 | 6 | 70 | 84 | 0 | 保存 ELF 直譯計數 |
| 自訂 MIN | 1 | 2 | 14 | 28 | 0 | 設計預期，未執行自訂 opcode |

核心動態由函式總數各減14條返回。Branch為4次taken、10次not-taken，核心4×1+10×2=24；自訂MIN核心每次1條，共14條。含返回時預期由38降至28，少10條、約26.32%；此為指令減少率，不能當作時間或cycle加速比。

### 3.3 5 Whys：為什麼合併比較與選值？

1. 為什麼提出MIN？原14筆Branch核心24條，設計預期MIN只要14條。
2. 為什麼可以減少？將有號比較與條件式複製合併成一個操作。
3. 為什麼保持語意？依有號大小選原來源位元，符合baseline兩條路徑。
4. 為什麼不直接稱為加速？沒有資料路徑延遲、時脈與cycle的證據。
5. 為什麼只比較指令數？HOMEWORK.md第5.4節明定CP3不要求cycle。

## 4. 遭遇的問題與解法

本次整合發現主報告仍有兩組Git衝突標記，導致章節與完成狀態互相矛盾。已整合成唯一報告，並區分小組採用編碼與教師核准來源。附件的funct7位元範圍誤寫32:25、第三筆Hex誤植為0x0118178B，分別修正為31:25及0x0118078B，並加入逐欄反解核對。以上為本次實際發現與修正，非替組員虛構個人經驗。

本次 AI 協助檢查發現，保存 ELF 的 `min_s32` 是由 C 編譯而來，而目前另有同名 `min_s32.S`；若只看符號名稱，容易把兩份來源的證據混用。因此改以明確的 `min_branch` 作對照，核對 ELF 雜湊、目前 Branch 原碼與快照的一致性，以及保存的指令形狀，不把執行舊 ELF 寫成重新編譯。目前檢查仍是 RV32I 子集合直譯，不宣稱完整處理器認證。

### 4.1 我的交接紀錄：目錄調整後如何保留既有成果

在整理 CP3 工作二時，我發現專案目錄調整後，部分 README 仍保留 CP1、CP2 原本使用的路徑。雖然程式測試可以通過，但其他組員如果直接按照文件操作，仍可能因為路徑錯誤而無法重現結果。

因此，我將問題分成程式正確性與文件可重現性兩個部分進行確認，除了檢查測試結果，也比對編譯指令、清理流程及原有檔案是否完整保留。後續驗證確認 C baseline 的 14 筆測試通過，相關文件路徑也已修正。這讓我了解到，多人專題除了程式正確，也必須確保交接文件可以實際使用。

以上問題與解法由本人確認採用；文件修改、編譯、清理測試及差異分析由 Codex 協助執行，不將工具操作寫成本人手動完成。

### 4.2 5 Whys：目錄調整後，文件操作指令為何失效？

1. **為什麼照 README 操作會失敗？** 因為命令仍指向已不存在的 `instructions/02_MIN/`，目前實際位置已是 `src/`。
2. **為什麼程式搬好了，命令卻仍指向舊位置？** 因為路徑不只存在於程式或連結，也散落在多份 README 的命令與目錄敘述；第五筆搬遷後仍有未同步的使用入口。
3. **為什麼既有檢查沒有攔下這些入口？** 因為語意測試驗證結果，Markdown連結檢查驗證連結；命令區塊並不是一般連結，不在該項檢查的涵蓋範圍。
4. **為什麼通過這些檢查仍不能證明可交接？** 因為功能正確、檔案完整與讀者能依文件重現是不同要求，還需要逐一執行現行命令及確認平台產物，包括Windows的`.exe`目標與clean。
5. **為什麼需要全範圍清單，而不是只補已發現的命令？** 第八筆修復指定文件後，兩份程式目錄README仍漏修，第九筆才全面掃描並執行暫存驗證；這支持本次根因歸納：搬遷驗收範圍曾未涵蓋所有文件操作入口，逐點修補不能保證完整承接。

已採取的修正是統一路徑與平台前提、明確Windows目標、保留歷史紀錄、在暫存副本實跑建置及清理，並核對證據與Git歷史。避免再次發生的方法是每次搬遷先列出受影響的規格、報告、README、命令與建置輸出，再分別檢查連結、指令執行、來源及產物完整性。此因果整理由既有Git差異及驗收紀錄支持，不是假設本人當時已獨立找到根因。

## 5. 白話說明

MIN 指令的功能就是從兩個整數中選出比較小的數字。例如輸入 5 和 9，結果是 5；輸入 -5 和 9，結果則是 -5。因為 MIN 使用有號整數比較，所以必須正確判斷負數，不能直接使用無號比較。這條指令只需要比較並選擇其中一個數值，不必進行加減運算，因此不會因為計算而產生溢位。最後再將結果寫入指定暫存器。
