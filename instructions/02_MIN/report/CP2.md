## 1. 本次目標

在不改變 CP1 `min_s32(int32_t rs1, int32_t rs2)` 有號比較語意的前提下，以 RV32IM 組合語言實作 `MIN` 的 **Branch（分支）**與 **Branchless（無分支）**兩種版本，對照既有 C 函式經 `-O2` 編譯後的機器碼；驗證結果正確性，並統計靜態指令數、動態指令數與條件分支數。

## 2. 設計內容

### 2.1 規格與比較基準

- **輸入：**`rs1`、`rs2` 為 signed 32-bit（二補數）整數。函式呼叫遵循 RV32 的暫存器慣例，分別由 `a0`、`a1` 傳入。
- **輸出：**`rd = min(rs1, rs2)`；函式回傳值放在 `a0`。相等時回傳該共同值。
- **邊界：**必須正確處理 `INT32_MIN = -2147483648`、`INT32_MAX = 2147483647`；僅比較與選擇，沒有算術溢位問題。
- **C Baseline：**使用原有 [`../c_baseline/min.c`](../c_baseline/min.c) 的 `min_s32()`，非重新設計另一個 C 比較函式。
- **RV32IM 實作：**[`../rv32im/min_branch.S`](../rv32im/min_branch.S)、[`../rv32im/min_branchless.S`](../rv32im/min_branchless.S)。

原有 C 函式：

```c
int32_t min_s32(int32_t rs1, int32_t rs2)
{
    return (rs1 < rs2) ? rs1 : rs2;
}
```

### 2.2 Branch：條件分支實作

以下為測試產物的關鍵機器指令，已用 `objdump` 驗證（`addi rd, rs, 0` 相當於暫存器複製）：

```asm
min_branch:
    blt  a0, a1, done  # 若 a0 < a1，a0 已是答案
    addi a0, a1, 0     # 否則回傳 a1
done:
    jalr zero, 0(ra)   # 返回（ret）
```

當 `a0 < a1` 時只執行 `blt`、`jalr` 共 **2 條**；當 `a0 >= a1` 時還要執行 `addi`，共 **3 條**。條件比較使用有號 `blt`，不是無號比較。

### 2.3 Branchless：遮罩選擇實作

```asm
min_branchless:
    slt  t0, a0, a1
    sub  t0, zero, t0
    xor  t1, a0, a1
    and  t1, t1, t0
    xor  a0, a1, t1
    jalr zero, 0(ra)
```

`slt` 產生 0/1；`sub t0, zero, t0` 將它轉為 `0x00000000` 或 `0xFFFFFFFF` 的 **Mask（遮罩）**；隨後以 `xor`、`and` 依遮罩選擇較小值。此版本不含條件分支，但每次固定執行 **6 條**，而且會使用 `t0`、`t1` 兩個 caller-saved（呼叫端保存）暫存器。

### 2.4 編譯器產生的 C Baseline

本次使用 GCC 16.2.0、`-O2` 編譯原有 C 程式，實際反組譯為：

```asm
min_s32:
    bge  a0, a1, 10008
    addi a1, a0, 0
    addi a0, a1, 0
    jalr zero, 0(ra)
```

此版本在 `a0 < a1` 時依序執行 `bge`、兩個 `addi`、`jalr`，共 **4 條**；否則跳過第一個 `addi`，共 **3 條**。這是**本次 GCC 的特定輸出**，不能當作所有編譯器都會產生的固定結果。

### 2.5 5 Whys：為什麼選擇 Branch 作為本次指令數較少的方案？

1. **為什麼 Branch 的 14 組動態指令較少？**量測結果為 38 條，C Baseline 為 46 條，差 8 條。
2. **為什麼差 8 條？**在 14 組測資中有 4 組符合 `a0 < a1`；這類輸入每次 Branch 執行 2 條，GCC C Baseline 執行 4 條，合計少 `4 × 2 = 8` 條。
3. **為什麼 Branch 在這些輸入只要 2 條？**`a0` 已經是答案，`blt` 可以直接跳到 `jalr`，不用搬移資料。
4. **為什麼 GCC C Baseline 在相同輸入執行 4 條？**本次反組譯顯示先用 `addi` 把 `a0` 複製到 `a1`，再複製回 `a0`，形成兩次可避免的暫存器搬移。
5. **為什麼不能據此宣稱 Branch 普遍更快？**比較結果依賴 GCC 16.2.0 的實際編譯產物與測資分布；先前 Clang 17 的參考實驗曾產生 3 條的 C Baseline，且本次未量測 Pipeline（管線）週期或實際執行時間。

### 3.3 指令數比較（以原有 14 組 CP1 測資計算動態數據）

| 實作                                  |    靜態指令 | 靜態條件分支 | 14 組動態指令 | 14 組動態條件分支 | 分支成立次數 | 每次動態指令 |
| ------------------------------------- | ----------: | -----------: | ------------: | ----------------: | -----------: | ------------ |
| C Baseline `min_s32`（GCC `-O2`） |           4 |            1 |            46 |                14 |           10 | 3～4         |
| Branch `min_branch`                 | **3** |            1 |  **38** |                14 |            4 | 2～3         |
| Branchless `min_branchless`         |           6 |  **0** |            84 |       **0** |            0 | 固定 6       |

比較同一組 14 筆資料、相同的函式邊界與返回指令計數方式：

- **Branch 相較 GCC C Baseline**：動態指令數減少 `(46 − 38) / 46 × 100% = 17.39%`。
- **Branchless 相較 GCC C Baseline**：動態指令數由 46 增至 84；雖然消除條件分支，但無法據此判斷真實時間一定更慢或更快。
- **為何是 46 與 38？**14 組中 `a0 < a1` 有 4 組，其餘 `a0 >= a1` 有 10 組。C Baseline 為 `4 × 4 + 10 × 3 = 46`；Branch 為 `4 × 2 + 10 × 3 = 38`。
- 分支成立次數的差異來自兩者使用相反條件：C Baseline 使用 `bge`，Branch 使用 `blt`；**不能單憑成立次數推論分支預測成本**。

**限制：**17.39% 是本次測資上的「動態指令數減少比例」，**不是**實際執行時間、Cycle 或功耗改善比例。另一編譯器（如 Clang 17）可能生成不同的 C Baseline 機器碼，故跨編譯器數值不可混為同一次實驗結果。

## 4. 遭遇的問題與解法

**問題一：如何避免編譯後不必要的暫存器搬移？**這是本次反組譯與指令數比較中觀察到的最佳化機會，而不是 C 程式的正確性錯誤。GCC 16.2.0 以 `-O2` 編譯原有 `min_s32()` 後，使用 `bge` 判斷；當 `a0 < a1` 時，仍連續執行 `addi a1, a0, 0` 和 `addi a0, a1, 0`，將已經在 `a0` 的答案搬到 `a1` 再搬回 `a0`。手寫 Branch 版本改用 `blt`，在 `a0 < a1` 時直接跳至返回指令，避免這兩次搬移。透過 `objdump` 逐條核對，該路徑的指令數由 4 條減至 2 條；本次 14 組 CP1 測資有 4 組符合此條件，因此合計減少 8 條動態指令（46 → 38，減少 17.39%）。這是**同一組測資、同一計數範圍**下的指令數比較，尚不能推論真實執行時間改善。

**問題二：消除條件分支是否必然降低指令數？**無分支版本使用 `slt`、`sub` 與位元運算進行遮罩選擇，確實使條件分支數降為 0，但每次固定執行 6 條指令，14 組合計 84 條，高於 Branch 的 38 條。因此本次以**指令數**為評估指標時，Branch 較精簡；Branchless 是否有時間上的優勢，需要額外測量處理器分支預測、Pipeline 和實際週期數，不能僅以目前結果判斷。

**比較限制：編譯器輸出並不固定。**先前 Clang 17 的參考量測顯示 C Baseline 為 3 條靜態指令、14 組合計 38 條動態指令；本次 Mac 上的 GCC 16.2.0 則得到 4 條靜態、46 條動態。這兩次量測使用不同編譯器，不能把先前結果併入本次 GCC 的改善比例。
