# CP1 — MIN C Baseline

## 1. 本次目標

以 C 語言建立 `MIN` 指令的黃金參考模型，定義 32-bit 有號整數取最小值的行為，並以正常值、相等值、正負號及邊界值驗證實作。

## 2. 設計內容

### 2.1 函式規格

```c
int32_t min_s32(int32_t rs1, int32_t rs2);
```

- 輸入：`rs1`、`rs2`，兩者皆為 32-bit 有號整數。
- 輸出：兩者中數值較小者。
- 公式：`rd = min(rs1, rs2)`。
- 相等時：回傳相同值。
- 溢位：本函式只做比較及選擇，不做加減乘除，因此不會產生算術溢位。

核心實作如下：

```c
return (rs1 < rs2) ? rs1 : rs2;
```

選用 `int32_t` 是為了明確對應 RV32 的 32-bit 暫存器寬度，並確保 `0xFFFFFFFF` 以有號值解讀時代表 `-1`，而非無號值 `4294967295`。

### 2.2 測試方法

[test_min.c](../tests/test_min.c) 使用表格驅動測試：每筆資料包含名稱、`rs1`、`rs2` 與預期結果。程式逐筆呼叫 `min_s32`，比較實際值與預期值，最後輸出通過數量；若有任一錯誤，程式以非 0 狀態碼結束。

測資包含：

1. 教師提供的兩組案例。
2. 正整數依不同輸入順序比較。
3. 兩個負數、正負混合及包含零的比較。
4. `INT32_MIN`、`INT32_MAX` 及兩端點相等的邊界案例。

### 2.3 5 Whys：為什麼使用 `int32_t`？

1. 為什麼不用一般 `int`？因為 C 標準未保證 `int` 一定是 32-bit。
2. 為什麼需要固定 32-bit？因為本專題目標 ISA 是 RV32，暫存器資料寬度為 32-bit。
3. 為什麼位元寬度會影響 MIN？因為最高位在有號表示中是符號位，寬度不同會改變可表示範圍與位元解讀。
4. 為什麼不能使用 `uint32_t`？因為題目要求有號比較，無號比較會把 `0xFFFFFFFF` 視為很大的正數。
5. 為什麼此決策可驗證？測資直接涵蓋 `INT32_MIN`、`INT32_MAX`、`-1` 與 0，可檢查實作是否符合 32-bit 有號語意。

## 4. 遭遇的問題與解法

設計測資時最容易忽略的是「有號」語意。若把參數或測資寫成 `uint32_t`，位元樣式 `0xFFFFFFFF` 會被視為 `4294967295`，與題目要求的 `-1` 比較結果不同。解法是讓函式介面、測資欄位與輸出格式全部使用 `int32_t`，並加入 `INT32_MIN`、`INT32_MAX`、`-1` 與 0 的案例；同時使用 `PRId32` 輸出，以避免不同平台的格式不一致。

## 5. 白話說明

MIN 就像把兩個數字放在一起比大小，留下較小的那一個。這次先用 C 程式做出可信任的標準答案，之後寫 RISC-V 組合語言或自訂指令時，都能拿相同測資來核對。重點不只在一般正數，也要確認負數、兩數相等、零，以及 32-bit 能表示的最大與最小值。只要所有版本對同一批輸入都得到相同結果，就能較有把握地判斷後續實作沒有改變指令語意。
